# ML-модель оценки кредитного риска

## 1. Задача

ML-компонент решает задачу многоклассовой классификации: по параметрам компании и кредитной заявки предсказать категорию риска.

Классы, используемые в проекте:

- `low_risk`;
- `medium_risk`;
- `high_risk`;
- `very_high_risk`.

Названия классов являются категориями модели. Они не означают автоматическое одобрение или отказ без отдельной кредитной политики.

## 2. Алгоритм

В проекте используется CatBoost — алгоритм градиентного бустинга над деревьями решений, подходящий для табличных данных и поддерживающий категориальные признаки.

Для многоклассовой задачи модель может возвращать:
- предсказанный класс (`predict`);
- вероятности по классам (`predict_proba`), если этот метод используется в коде интеграции.

Порядок вероятностей должен соответствовать `model.classes_`. Нельзя сопоставлять значения вероятностей с названиями классов по предположению или вручную заданному порядку.

## 3. Признаки

В ходе разработки обсуждались следующие группы признаков компании и заявки:

| Признак | Смысл | Тип |
|---|---|---|
| `company_age` | Возраст компании | Числовой |
| `industry_okved` | Отрасль / код ОКВЭД | Категориальный |
| `revenue_last_year` | Выручка за прошлый год | Числовой |
| `net_profit` | Чистая прибыль | Числовой |
| `existing_debt` | Существующая долговая нагрузка | Числовой |
| `requested_amount` | Запрашиваемая сумма | Числовой |
| `credit_history_status` | Категория кредитной истории | Категориальный |
| `loan_purpose` | Цель кредита | Категориальный |

**Важно:** этот список следует сверить с фактическим списком признаков, передаваемых в `fit` и `predict`. Названия, типы и порядок столбцов в обучении и инференсе должны совпадать.

## 4. Данные и обучение

В проекте использовался синтетический набор данных для прототипирования. Он позволяет проверить технический процесс обучения и интеграцию модели, но сам по себе не доказывает, что модель сможет надёжно оценивать риск реальных компаний.

Рекомендуемый воспроизводимый процесс:

1. зафиксировать генератор данных и random seed;
2. проверить распределение целевого класса и диапазоны признаков;
3. разделить данные на train/validation/test без утечки целевой переменной;
4. обучить модель только на train;
5. выбрать параметры на validation;
6. однократно оценить итоговое качество на test;
7. сохранить модель, список признаков и версию обучающего набора.

Точные параметры и команды обучения нужно брать из скриптов в `ml/`.

## 5. Оценка качества

Для многоклассовой модели недостаточно сообщать только accuracy. Следует приводить:

- accuracy;
- precision, recall и F1-score по каждому классу;
- macro-F1 и weighted-F1;
- матрицу ошибок;
- при наличии корректно рассчитанных вероятностей — подходящие multiclass-метрики и оценку калибровки.

Ранее в процессе разработки на тестовой выборке из 1600 наблюдений фиксировалась accuracy около `0.6406`. Это исторический результат из рабочих материалов, а не подтверждение качества текущего файла модели. Перед публикацией цифры нужно повторно получить из актуального эксперимента и указать метод разделения данных.

## 6. Использование результата

Рекомендуемый формат результата скоринга на концептуальном уровне:

```json
{
  "risk_class": "medium_risk",
  "probabilities": {
    "low_risk": 0.15,
    "medium_risk": 0.55,
    "high_risk": 0.20,
    "very_high_risk": 0.10
  }
}
```

Это **иллюстративный пример формата**, а не подтверждённый контракт API и не реальный прогноз модели. Фактический формат определяется реализацией.

## 7. Ограничения и контроль качества

- Синтетическая разметка может быть слишком простой или отражать правила генератора, а не реальные закономерности дефолта.
- Качество необходимо проверять на данных, не участвовавших в обучении и настройке.
- Следует анализировать ошибки по каждому классу, особенно для категорий высокого риска.
- Вероятности модели не обязательно хорошо откалиброваны.
- Перед применением в финансовом решении необходимы объяснимость, мониторинг, проверка смещений и экспертный контроль.
